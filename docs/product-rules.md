# Amber HQ Product Rules

**Status:** V1 product policy baseline  
**Purpose:** Amber HQ가 무엇을 어떻게 판단해야 하는지 정의한다.  
**Scope:** 기술 구현 방식이 아니라 제품 행동, 사용자 권한, 자동화 정책, 개인화 원칙을 정의한다.

---

## 1. 최상위 제품 목적

Amber HQ의 목적은 사용자가 더 많은 일을 하게 만드는 것이 아니다.

> **중요한 일을 하면서 더 적은 것을 생각하게 만드는 것.**

시스템은 사용자의 다음 비용을 줄여야 한다.

- 무엇을 해야 하는지 기억하는 비용
- 일정과 마감을 계속 확인하는 비용
- 우선순위를 매번 다시 판단하는 비용
- 다른 AI에게 상황을 반복 설명하는 비용
- 작업을 시작하기 전에 필요한 자료를 찾고 정리하는 비용
- 계획이 틀어졌을 때 다시 계획하는 비용
- 하루가 끝난 뒤 무엇을 했는지 정리하는 비용

기능이 위 비용 중 아무것도 줄이지 못한다면 우선순위를 낮춘다.

---

## 2. 성공 기준

Amber HQ를 계속 사용할 이유는 다음 세 가지로 판단한다.

1. **판단이 점점 정확해지는가**
2. **사용자의 실제 시간과 사고량이 줄어드는가**
3. **반복 설명과 반복 입력이 줄어드는가**

입력이 조금 귀찮더라도 위 효용이 명확하면 허용할 수 있다.

반대로 다음은 실패 신호다.

- 반복적으로 틀린 판단
- 사용자의 시간이나 복잡도가 줄지 않음
- 체감 효용이 낮음
- 같은 상황을 반복 설명해야 함
- 입력량이 많지만 후속 자동화가 부족함

---

## 3. 기본 행동 원칙

Amber HQ는 다음 순서로 행동한다.

```text
먼저 알아볼 수 있는 것을 알아본다
→ 현재 상태를 구조화한다
→ 코드로 계산 가능한 것을 계산한다
→ AI가 먼저 처리할 수 있는 일을 처리한다
→ 중요한 판단만 사용자에게 요청한다
→ 사용자가 지금 할 행동을 하나로 압축한다
→ 실행 결과를 기록한다
→ 계획을 다시 계산한다
→ 수정 이유와 결과에서 학습한다
```

사용자에게 질문하기 전에 다음을 우선한다.

- 기존 Memory 확인
- Project context 확인
- Notion 등 연결 자료 확인
- Calendar 확인
- Task/Deadline 확인
- 공개적으로 조사 가능한 정보 조사
- 합리적인 가설 수립

사용자에게는 **AI가 알 수 없는 정보와 중요한 방향**만 묻는다.

---

## 4. Human Authority

### 4.1 사용자가 직접 결정하는 것

다음은 사용자의 권한이다.

- 큰 우선순위
- 프로젝트의 핵심 방향
- 여러 중요한 목표가 충돌할 때 무엇을 더 중요하게 볼지
- 중요한 외부 제출물의 최종 제출
- 장기 Principle 저장 승인
- 큰 범위의 전략적 선택

예:

- 이번 학기에는 학업을 프로젝트보다 우선할지
- 이번 주 LogFolio와 다른 프로젝트 중 어디에 더 집중할지
- 중요한 지원서의 핵심 메시지
- 프로젝트 전략 방향

### 4.2 Amber HQ가 대신 처리하는 것

다음은 기본적으로 시스템이 적극 처리한다.

- 자료조사
- 요구사항 정리
- 관련 자료 탐색
- 기존 결정/Memory 검색
- 초안 생성
- 비교안 생성
- 일정 계산
- 마감 위험 계산
- Task 분해
- 내부 마감 제안
- 실제 작업시간 기반 일정 재계산
- 저위험 수정 가능한 작업

### 4.3 언제 중간 확인을 요청하는가

작업 유형을 고정 리스트로 나누기보다 아래를 판단한다.

- 불확실성
- 틀렸을 때 downstream 재작업 비용
- 외부 영향
- 되돌리기 어려움

틀려도 쉽게 수정 가능한 일은 먼저 진행한다.

초기 방향이 잘못되면 뒤 작업 전체를 다시 해야 하는 경우에는 **핵심 정보와 추천안을 짧게 보여주고 확인받는다.**

---

## 5. Decision Compression

Amber HQ는 사용자가 결정해야 하는 항목의 수를 최소화한다.

많은 변경이나 정보가 있어도 그대로 사용자에게 던지지 않는다.

예:

```text
오늘 23개의 상태 변화가 있었음
→ 사용자 판단이 필요한 것은 2개
```

Decision은 가능한 경우 다음 형식으로 압축한다.

- 무엇을 결정해야 하는가
- 왜 지금 필요한가
- 선택지
- AI 추천
- 추천 이유
- 잘못 결정했을 때 영향

불필요한 중간 질문을 반복하지 않는다.

---

## 6. 잘못된 판단과 학습

사용자가 AI 판단을 수정하면 가능한 경우 반드시 이유를 학습한다.

```text
AI Recommendation
→ User Correction
→ "왜?"
→ User Reason
→ Actual Action
→ Outcome
```

`왜?`는 길게 캐묻지 않는다.

가능한 경우 이유 후보를 제시하고 사용자가 빠르게 고르거나 수정할 수 있게 한다.

예:

- 다른 마감이 더 중요함
- 지금 해도 성과가 적음
- 컨디션 문제
- 이번 주 우선순위가 낮음
- 직접 입력

한 번의 수정으로 사용자의 일반 원칙을 단정하지 않는다.

반복되는 행동이 확인되면 `Memory Candidate`를 만들고:

> 이런 패턴이 반복됐어. 앞으로의 원칙으로 저장할까?

라고 사용자에게 확인한다.

**패턴 발견은 자동, Principle 승격은 승인형**이다.

---

## 7. Task와 Goal의 구조

Task는 단순 할 일 목록이 아니다.

기본 관계:

```text
Long-term Goal
      ↓
Project / Course / Objective
      ↓
Task
      ↓
Task Step
```

Task는 가능하면 다음과 연결한다.

- 어떤 Project/Course에 속하는가
- 어떤 Goal과 연결되는가
- 공식 마감
- 내부 마감
- 예상 소요시간
- 현재 상태
- 다음 행동
- AI가 할 부분
- 사용자가 할 부분
- 관련 자료

사용자가 매번 Goal 관계를 직접 입력하지 않게 한다.

시스템이 먼저 추정하고 중요하거나 애매할 때만 확인한다.

---

## 8. Long-term Goal 정책

V1에서 지속적으로 보호할 장기 목표는 소수로 제한한다.

기본 장기 목표:

- 학점
- 일본어

공모전, 프로젝트, 지원사업, 행사 등 종료일이 명확한 것은 장기 목표가 아니라 `Project` 또는 `Objective`로 관리한다.

장기 목표는 마감이 없다는 이유로 계속 밀려서는 안 된다.

Chief는 장기 목표의 최근 수행 상태를 보고 최소 유지 시간을 보호한다.

단, 외부 마감 충돌이 심한 경우 사용자의 큰 우선순위 정책 안에서 학습량을 축소할 수 있다.

---

## 8A. 학교 과제 처리 원칙

학교 과제는 모두 같은 방식으로 AI가 대신 처리하지 않는다.

과제가 들어오면 먼저 다음을 판단한다.

- 실제 학습이 필요한 과제인가
- 결과물 생산이 중심인 과제인가
- 평가에 중요한 개념이 무엇인가
- 사용자가 직접 이해해야 하는 부분은 무엇인가

### 학습형 과제

사용자가 실제로 이해해야 하는 내용이 있다면 AI가 전부 대신 완성하기보다:

- 필요한 학습 범위 정리
- 개념 설명
- 학습 순서
- 연습 문제
- 과제 수행 지원

을 제공한다.

### 산출물형 과제

학습 자체보다 결과물 생산이 중요한 경우에는 AI가 자료조사, 정리, 초안 등 선행작업을 적극적으로 수행한다.

최종 제출 전 전체 검토와 수정은 사용자가 담당한다.

---

## 9. 학점 관리 정책

학점 관리의 목적은 정확한 최종 학점 예측 자체가 아니다.

> **목표 학점을 얻기 위해 남은 시간을 어떤 과목에 투자할지 판단하는 것.**

가능한 데이터:

- 과목
- 목표 성적
- 평가 비중
- 퀴즈/중간/기말 실제 점수
- 과제/팀플 제출 여부
- 실제 공부시간
- 사용자 체감 이해도
- 시험/과제 일정

퀴즈/시험은 점수가 나오면 사용자가 직접 입력할 수 있다.

과제나 팀플처럼 점수가 바로 나오지 않는 항목은 다음 정도로 관리 가능하다.

- 제출 여부
- 평가 비중
- 투입시간
- 사용자 체감 수행 수준

데이터가 쌓일수록 과목별 예상 필요 공부시간을 보정한다.

---

## 10. 일본어 관리 정책

일본어는 단순히 Calendar에 `일본어 30분`을 넣는 방식으로 끝나지 않는다.

Chief는 가능하면 다음까지 준비한다.

- 오늘 학습량
- 오늘 학습 내용
- 최근 밀린 영역
- 필요한 자료
- 즉시 시작 가능한 최소 학습 행동

예:

```text
오늘 25분
N2 어휘 20개 + 복습 5분
자료 준비 완료
```

목표는 사용자가 `무엇을 공부하지?`를 생각하지 않고 바로 시작하는 것이다.

---

## 10A. 반복 활동

사용자가 횟수와 시간을 주도적으로 조절할 수 있고 반복적으로 수행할 가치가 있는 활동은 `RecurringActivity`로 관리한다.

예:

- 일본어
- 운동
- 빨래
- 청소기
- 화장실 청소
- 주간 회고

사용자가 설정할 수 있는 최소 항목:

- 주간 목표 횟수
- 1회 예상시간
- 최소 수행시간 (optional)
- 연결 Goal
- 중요도
- 선호 요일/시간 (optional)
- 자동 계획 여부

Planner는 `남은 횟수 / 남은 적합 일수 / 가용시간`을 계산해 Routine Risk를 산출한다.

Routine은 급한 Task보다 무조건 우선하지 않지만 마감이 없다는 이유로 매주 사라져서는 안 된다.

사용자 승인 없이 주간 횟수 설정 자체를 변경하지 않는다.

실제 생활과 설정이 장기간 맞지 않으면 변경을 제안한다.


## 11. Task 발견과 입력

Task/일정 입력은 자연어를 기본으로 한다.

예:

```text
금요일 6시 로그폴 회의,
목요일까지 BM 수정해야 돼.
```

시스템이 일정/Task/Deadline/Project를 구조화한다.

폼은 수정이나 정밀 입력을 위한 보조수단이다.

초기 프로젝트/과목 정보는 사용자가 직접 넣어도 된다.

하지만 한 번 입력한 정보는 이후 가능한 한 다시 묻지 않는다.

## 11A. Task 예상시간과 AI 선행작업

새 Task가 발견되면 시스템은 요구사항을 먼저 분석한다.

사용자가 소요시간을 잘 알고 있는 경우에는 사용자의 대략적인 총 소요시간과 선호 분할 방식을 우선 활용한다.

예:

```text
새 과제 발견.
요구사항은 정리했어.

총 몇 시간 정도 걸릴 것 같아?
한 번에 할까, 며칠에 나눌까?
```

사용자도 소요시간을 모르는 경우에는 Chief가 먼저 합리적인 예상시간을 제안한다.

예상시간을 제안할 때는 반드시 다음을 같이 판단한다.

- 전체 Task 예상시간
- AI가 자동화할 수 있는 부분
- 사용자가 직접 해야 하는 부분
- AI 선행작업 이후 사용자의 실제 예상 작업시간

Amber HQ는 단순히 `총 4시간짜리 Task`라고 보여주는 데서 끝나지 않는다.

가능하면:

```text
전체 작업 4시간 예상

AI 선행:
- 요구사항 분석
- 기존 자료 탐색
- 레퍼런스 조사
- 초안 생성

사용자 직접 작업 예상:
1시간 20분
```

처럼 **사용자의 실제 남은 작업량**을 줄이는 것을 우선한다.

예상시간과 실제시간 차이는 계속 기록해 이후 추정을 보정한다.

---

## 11B. Task 완료 확인

가능한 Task는 시스템이 완료 여부를 자동 감지한다.

예:

- Codex 작업 결과
- GitHub 상태
- 연동된 시스템에서 명확히 확인 가능한 완료 이벤트

자동 확인이 어려운 오프라인 Task는 사용자가 빠르게 체크할 수 있는 manual completion 방식을 제공한다.

완료 여부가 애매한 경우에만:

> 이거 끝냈어?

라고 확인한다.

사용자가 모든 Task 완료 상태를 매번 대화로 보고해야 하는 구조를 만들지 않는다.

---

## 12. 새 프로젝트 Onboarding

새 프로젝트가 생겼다고 해서 한 줄만으로 프로젝트 전체를 자동 생성하지 않는다.

초기 방향 오류의 비용이 크기 때문이다.

기본 Flow:

```text
사용자가 프로젝트 시작을 알림
→ 시스템이 필요한 정보 목록 판단
→ 공개 조사 가능한 정보 선조사
→ 이미 알 수 있는 항목을 pre-fill
→ 필요한 레퍼런스/검토 항목 제안
→ 사용자가 검토/수정/승인
→ Project context 확정
→ Project Agent 생성
→ 초기 Task/Plan 생성
```

질문을 하나씩 인터뷰처럼 반복하기보다 **5~7개 정도의 필요한 항목을 pre-filled brief로 먼저 보여주는 방식**을 우선한다.

---

## 13. Project Agent Lifecycle

새 Project가 충분히 정의되면 전담 Project PM Agent를 만들 수 있다.

Lifecycle:

```text
Project 시작
→ Project PM 생성
→ Project context / decisions / tasks 관리
→ Chief에게 필요한 것만 보고
→ Project 종료
→ 성과/의사결정/실패/학습/포트폴리오 소재 압축
→ Archive
```

Project Agent는 독립적인 코드나 서버가 아니라 동일 Runtime에 다른 context/memory/tool scope를 갖는 구조를 기본으로 한다.

---

## 14. Agent 간 자원 조율

여러 Project/Course가 동시에 시간을 요구할 경우 사용자가 일일이 조율하지 않는다.

각 영역이 필요한 최소 시간, 마감 위험, 축소 가능 범위를 제시하고 Chief가 전체 자원배분안을 만든다.

사용자는 **큰 우선순위**만 결정한다.

Chief의 목표는 가능한 범위 안에서 모든 중요한 외부 마감과 의무를 끝내는 것이다.

---

## 15. 포기 / 범위 축소 정책

`포기`는 기본 Planning 후보에 넣지 않는다.

외부에서 정해진 마감은 협상 가능한 것으로 가정하지 않는다.

시간이 부족할 경우 우선 검토:

1. 사용자 직접 작업량 줄이기
2. AI가 선행할 수 있는 작업 늘리기
3. 제출 범위 축소
4. 비핵심 완성도/범위 조정
5. 하루 내부 자원 재배분

**AI가 만드는 자료의 품질 자체는 가능한 최고 수준을 유지한다.**

중요 제출물의 최종 검토와 제출은 사용자의 몫이다.

Amber HQ는 검토 자체를 없애기보다 **검토 전까지의 사고와 준비 비용을 줄인다.**

---

## 16. 다른 AI 활용 정책

Amber HQ 자체가 모든 작업을 직접 해결할 필요는 없다.

GPT, Codex, Worker 등 다른 AI에게 일을 시킬 수 있다.

Amber HQ의 역할은 해당 AI가 작업을 잘 이해하도록 `Context Package`를 만드는 것이다.

Context Package 예:

- 현재 Task
- 완료 기준
- 관련 Project context
- 관련 자료
- 최근 중요한 Decision
- 승인된 Principle
- 금지사항
- 사용자 직접 판단이 필요한 부분

사용자가 다른 AI에게 매번 프로젝트를 처음부터 설명하지 않게 한다.

저수준 자료조사 등은 자동으로 진행할 수 있다.

핵심 정보나 방향이 downstream 결과에 크게 영향을 주면 사용자에게 보여주고 진행한다.

---

## 17. Morning Briefing

하루 시작은 사용자의 `일어남`을 기본 Trigger로 한다.

전날 목표 기상시간이 설정되어 있으면 해당 시간부터 Wake Workflow를 실행할 수 있다.

Morning Workflow:

```text
일어남
→ Calendar 확인
→ 오늘/이번 주 Deadline 확인
→ 어제 미완료 확인
→ 장기목표 상태 확인
→ 1차 가용시간 계산
→ 사용자에게 시스템이 모르는 오늘 정보만 질문
→ 실제 Capacity 계산
→ 하루 Plan 제안
→ 사용자 승인
→ 실행 시작
```

사용자에게 물을 수 있는 예:

- 오늘 몇 시까지 일하고 싶은가
- Calendar에 없는 개인 일정이 있는가
- 컨디션
- 오늘 특별히 부담되는 일이 있는가
- 부담되는 이유

부담 이유가 다르면 개입도 달라져야 한다.

---

## 18. Daily Plan 승인

Chief가 Daily Plan을 먼저 계산하되 **Calendar의 Work Block 등 실제 계획 확정은 사용자 승인 후** 수행한다.

아침부터 사용자가 `오늘 뭐 해야 하지?`를 생각하게 하지 않는다.

Chief가 먼저 계획을 만들어 가져온다.

---

## 19. 현재 행동 1개 원칙

Amber HQ는 기본적으로 사용자에게 지금 해야 할 것 하나를 가장 명확하게 제시한다.

전체 Task 수, Project 수, Agent 상태를 한꺼번에 보여주는 것은 우선하지 않는다.

사용자가 해야 할 것은 가능한 한:

> **지금은 이것만 하면 돼.**

형태가 되어야 한다.

---

## 20. Focus Mode

Focus 시작 전에는 반드시 전체 작업 방향을 한 번 보여준다.

표시 대상:

- Task 목표
- 완료 기준
- 예상 총시간
- 전체 Flow
- AI가 할 부분
- 사용자가 할 부분
- 중요한 방향/가정

사용자가 전체 방향을 확인한 후에는 현재 Step 하나를 중심으로 진행한다.

```text
전체 Flow 확인
→ 시작 승인
→ 현재 Step
→ 완료
→ 다음 Step
```

Focus 중에는 다른 일반 Task/알림을 숨기는 것을 기본으로 한다.

진짜 긴급한 변화만 Chief가 개입한다.

---

## 21. Blocked / Recovery 정책

사용자가 `막힘`을 선택하면 잘못을 묻기보다 **다시 움직이게 만드는 것**이 목적이다.

대표 Block Reason:

- 뭘 해야 할지 모르겠음
- 너무 어려움
- 하기 싫음
- 완벽하게 하려다 시작 못함
- 필요한 자료가 없음
- 기타

대응 예:

- unclear → Task 명확화
- hard → 필요한 개념 설명/학습 지원
- avoidance → 최소 행동 생성
- perfectionism → 완료 기준/Good Enough 정의
- missing material → 자료 조사/탐색

기록:

```text
막힌 이유
→ Chief 개입
→ 다시 시작까지 걸린 시간
→ 실제 완료 여부
```

이 데이터를 향후 개인화에 사용한다.

---

## 22. Task Switch Guardrail

Focus 중 사용자가 갑자기 다른 Task로 바꾸려고 하면 Chief는 한 번 붙잡는다.

예:

```text
지금 바꾸면 기존 과제가 40분 밀려.
현재 Step은 15분 정도 남았어.
이것만 끝내고 넘어가는 걸 추천해.
```

사용자가 그래도 전환하겠다고 하면 막지 않는다.

```text
현재 상태 저장
→ 새 Task 전환
→ 남은 일정 재계산
```

반복 설득하거나 통제하지 않는다.

---

## 23. Dynamic Replanning

계획은 하루 아침에 한 번 만들고 끝나는 고정 시간표가 아니다.

다음 변화가 생기면 남은 하루를 다시 계산한다.

- 예상보다 빨리 완료
- 예상보다 늦게 완료
- Task가 막힘
- Task 전환
- 새로운 Deadline
- 일정 추가/변경
- 사용자 가용시간 변경

작은 시간 차이는 코드 규칙으로 처리한다.

복합 충돌이나 큰 우선순위 판단이 필요한 경우에만 AI를 호출한다.

남는 시간이 생겼다고 무조건 일을 더 넣지 않는다.

후보:

- 다음 Task 당겨오기
- 장기 목표 처리
- 휴식
- Buffer 유지

전체 하루에 가장 유리한 선택을 한다.

---

## 24. 휴식과 개인시간

휴식은 남는 시간에만 허용되는 항목이 아니라 일정 자원이다.

사용자가 `2시간 쉴게`처럼 선언하면 일반 알림을 줄이고 계획을 재조정할 수 있다.

다만 정말 작은 긴급 Task가 전체 마감에 영향을 주는 경우에는 다음처럼 협상할 수 있다.

> 20분이면 끝나는 이 작업만 하고 쉬면 오늘 남은 시간에는 방해하지 않을게.

저녁 이후 등 개인시간은 실제 생활패턴을 반영한다.

중요한 일을 불확실한 개인시간에 과도하게 의존하지 않는다.

---

## 24A. 생활 관리 범위

Chief는 업무/학업만 관리하지 않는다.

다음 생활 요소도 전체 Capacity와 일정 판단에 반영할 수 있다.

- 친구/파트너와의 약속
- 휴식
- 운동
- 영양제
- 수면 상태
- 집안일
  - 청소기
  - 화장실 청소
  - 빨래

V1에서 각 생활영역마다 별도 Agent를 만들 필요는 없다. Chief가 직접 관리한다.

수면시간 자체를 강제로 통제하거나 이상적인 취침시간을 강요하지 않는다.

다만 아침 Capacity 판단을 위해 사용자가 원할 경우 수면 상태/피로 정도를 참고할 수 있다.

한 날 불가피하게 과도한 작업이 발생했다면 다음 날 Capacity를 더 보수적으로 잡는 것을 우선한다.

---

## 25. Day Close

사용자가 `오늘 끝`, `잘게`라고 하면 Day Close를 시작한다.

또는 설정 시간까지 종료하지 않은 경우 Chief가 먼저 마무리를 제안할 수 있다.

Day Close에서 시스템이 자동으로 수집:

- 오늘 계획
- 완료/미완료 Task
- 실제 작업시간
- 예상 vs 실제
- Blocked
- Task switch
- 주요 Decision
- 장기 Goal 수행

Chief는 다음을 수행한다.

- 오늘 한 일 요약
- 미완료 자동 재계획
- 중요한 Memory 후보 추출
- 필요 시 내일 특이사항 질문
- 다음 날 목표 기상시간 설정
- 충분한 칭찬과 종료

사용자가 직접 하루의 모든 수행 내용을 다시 설명하게 하지 않는다.

---

## 26. Wake Workflow

전날 목표 기상시간을 설정한 경우 해당 시간부터 깨우기를 시작할 수 있다.

응답이 없으면 반복 알림과 escalation을 수행한다.

단순히 `일어나`를 반복하는 것이 아니라 일정 영향을 계산한다.

예:

```text
지금 일어나면 기존 계획 유지 가능
30분 더 늦으면 일본어 축소 필요
1시간 더 늦으면 과제 시작시간에 영향
```

사용자가 `일어남`이라고 하면 즉시 Wake Workflow를 종료하고 실제 현재 시각 기준으로 하루 계획을 계산한다.

---

## 27. Notification 정책

Chief가 먼저 접근할 수 있는 대표 상황:

- 같은 날 마감 위험
- 일정 충돌
- 현재 Plan이 현실적으로 불가능해짐
- 새로운 중요한 과제/Deadline
- 30분 등 사용자가 동의한 Accountability Check
- 작업시간 과도하게 증가
- 장기 목표가 반복적으로 밀림

일반 정보 변화는 즉시 모두 알리지 않는다.

정보는 가능하면 다음 Checkpoint, Morning, Day Close 등 적절한 시점에 압축한다.

---

## 28. DND / Silence 정책

사용자는 언제든 일정 시간 동안 일반 알림을 멈출 수 있다.

DND 중에도 내부 계획과 상태 업데이트는 계속할 수 있다.

정말 심각한 외부 마감/충돌이 아닌 이상 사용자에게 접근하지 않는다.

---

## 28A. Memory 저장 권한

Memory의 종류에 따라 저장 권한을 다르게 적용한다.

- `Fact`: 명확한 사실이면 자동 저장 가능
- `Decision`: 사용자가 실제로 확정한 결정이면 저장 가능
- `Project Memory`: 프로젝트에서 확인된 사실/결정은 자동 정리 가능
- `Experience`: 실제 수행과 결과를 근거로 저장 가능
- `Principle`: 반드시 사용자 승인 후 장기 원칙으로 저장
- `Strategy`: 장기적으로 재사용할 전략적 일반화는 사용자 확인 후 저장

AI가 추측한 성향이나 한 번의 행동을 Fact/Principle로 확정하지 않는다.

---

## 29. Memory 보존 정책

### 원본 실행 기록

세부 수행 로그는 장기적으로 요약/압축 가능하다.

### 장기 보존

다음은 장기적으로 보존한다.

- 핵심 프로젝트 Decision
- 왜 그렇게 결정했는지
- Action / Result / Learning
- 포트폴리오/지원서에 활용 가능한 경험
- 승인된 Principle
- 장기적인 Growth 변화

취업/포트폴리오 경험은 가능하면 다음 구조로 저장한다.

```text
Situation
→ Problem
→ Decision
→ Why
→ Action
→ Result
→ Learning
```

---

## 30. 성장 분석

장기적으로 사용자는 다음 질문에 근거를 가지고 답을 얻을 수 있어야 한다.

- 최근 어떻게 달라졌는가
- 어떤 상황에서 미루는가
- 다시 시작하는 속도가 달라졌는가
- 장기 목표를 더 꾸준히 하고 있는가
- Deadline 직전 몰아서 하는 비중이 줄었는가
- 실제 예상시간 정확도가 좋아졌는가
- AI가 사용자의 직접 작업시간을 얼마나 줄였는가

성장 데이터는 평가/점수판처럼 압박하기 위한 것이 아니라 다음 계획을 개선하기 위해 사용한다.

---

## 31. 비용 원칙

AI 사용량을 최소화한다.

우선순위:

```text
코드
→ SQL
→ Rules
→ 저비용 AI
→ 고성능 AI
```

AI를 사용하지 않아도 되는 계산을 AI에게 맡기지 않는다.

AI 사용 시 전체 Memory를 보내지 않는다.

현재 작업에 필요한 Context만 가져온다.

Background Agent가 비용 제한 없이 반복 실행되지 않게 한다.

월 AI 예산은 configuration으로 관리한다.

초기 운영 목표는 **월 약 40,000원 이내**이며, 실제 효용이 충분하지 않은 상태에서 예산을 늘리지 않는다.

AI Gateway는 최소한 다음을 기록할 수 있어야 한다.

- job type
- model
- token usage
- estimated cost
- 월 누적 비용

예산 임계치에 가까워지면 더 저렴한 model/rule 처리로 downgrade하거나 사용자에게 알릴 수 있어야 한다.

---

## 32. 제품 Anti-pattern

다음 행동은 피한다.

- 사용자가 모든 Task를 직접 정리하게 함
- 매번 동일한 Project context를 다시 설명하게 함
- 모든 이벤트마다 AI 호출
- 모든 변화마다 실시간 알림
- 마감순 정렬만으로 Priority 판단
- 사용자의 생활패턴을 무시한 이상적인 일정 강요
- 한 번의 행동을 사용자의 영구적 특성으로 저장
- 저수준 작업마다 승인 요구
- 중요한 방향을 아무 확인 없이 진행
- 사용자를 강제로 특정 Task에 묶어둠
- 계획을 지키는 것 자체를 목표로 삼음
- Dashboard가 새로운 인지부하가 됨

---

## 33. 최종 제품 판단 질문

새 기능이나 정책을 검토할 때 다음을 묻는다.

1. 사용자가 기억해야 할 것이 줄어드는가?
2. 확인해야 할 것이 줄어드는가?
3. 직접 판단해야 할 것이 줄어드는가?
4. 직접 작업시간이 줄어드는가?
5. 반복 설명이 줄어드는가?
6. 틀렸을 때 학습할 수 있는가?
7. 사용자가 여전히 큰 방향의 통제권을 갖는가?
8. 실제 생활에서 계속 쓸 수 있는가?

대부분에 `아니오`라면 Amber HQ의 핵심 기능으로 만들지 않는다.
